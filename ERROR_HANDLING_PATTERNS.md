# Error Handling Patterns Analysis - ip-me Codebase

## Overview
The ip-me codebase implements a comprehensive, multi-layered error handling strategy across server-side API routes, client-side hooks, and UI components. The approach prioritizes user experience while maintaining developer-friendly debugging capabilities.

---

## 1. ERROR BOUNDARY (src/app/error.tsx)

### Architecture
- **Type**: Next.js App Router Error Boundary (Client Component)
- **Scope**: Catches unhandled errors during rendering in the `/app` directory
- **Purpose**: Provides graceful fallback UI when critical errors occur

### Key Patterns

#### Error Interface
```typescript
interface ErrorProps {
  error: Error & { digest?: string };
  reset: () => void;
}
```

- `error.digest`: Unique error identifier (generated by Next.js) for tracking
- `reset()`: Function to retry the failed component tree

#### Error Display Strategy
1. **User-Facing Message** (Always visible):
   - Generic, friendly language: "Something went wrong"
   - Helpful context about what failed
   - Suggests possible causes (network issues, unexpected errors)

2. **Developer Details** (Development-only):
   - Shows full error message in monospace font
   - Displays error digest/ID for tracking
   - Only visible when `process.env.NODE_ENV === 'development'`

#### User Recovery Options
- **Retry Button**: Calls `reset()` to re-render the component tree
- **Help Link**: Links to GitHub issues for manual reporting
- **Visual Feedback**: Red error icon and destructive styling

### UI Structure
```
┌─────────────────────────────────┐
│   Error Icon (Red)              │
│   "Something went wrong"         │
│   Generic error message          │
│   [Dev Details - if development]│
│   [Retry Button]                │
│   [Report Issue Link]           │
└─────────────────────────────────┘
```

## 2. API ROUTE ERROR HANDLING (src/app/api/detect-ip/route.ts)

### Architecture
- **Type**: Next.js Route Handler (Server-side)
- **Validation Layer**: Zod schema validation
- **Error Response Format**: Standardized APIError type

### Error Types Handled

#### 1. Validation Errors (400 Bad Request)
```typescript
// Invalid IP format
if (!validateIP(queryIP)) {
  return createErrorResponse(
    'Invalid IP address format',
    ERROR_CODES.INVALID_IP,
    400,
    { provided: queryIP, expected: 'Valid IPv4 or IPv6 address' }
  );
}
```

**Pattern**: 
- Input validation happens early
- Returns 400 with specific details about validation failure
- Includes context (what was provided vs. what's expected)

#### 2. Missing Required Data (400 Bad Request)
```typescript
if (!ip) {
  return createErrorResponse(
    'No IP address provided and unable to detect from headers',
    ERROR_CODES.NO_IP_PROVIDED,
    400
  );
}
```

**Pattern**:
- Checks both explicit parameter and header fallback
- Clear message about what's missing

#### 3. Zod Schema Validation (500 Server Error)
```typescript
if (error && typeof error === 'object' && 'issues' in error) {
  return createErrorResponse(
    'Failed to validate API response',
    ERROR_CODES.VALIDATION_FAILED,
    500,
    { zodError: error }
  );
}
```

**Pattern**:
- Catches validation errors from response schema
- Distinguishes from input validation errors
- Includes validation error details for debugging

#### 4. Generic Server Errors (500 Server Error)
```typescript
return createErrorResponse(
  'IP detection service temporarily unavailable',
  ERROR_CODES.SERVICE_UNAVAILABLE,
  500
);
```

**Pattern**:
- Fallback catch-all for unexpected errors
- Generic message to avoid leaking sensitive info
- Always logged to console for investigation

### Standardized Error Response

```typescript
interface APIError {
  error: string;                      // User-friendly message
  code: string;                       // Machine-readable error code
  details?: Record<string, unknown>;  // Additional context (optional)
}

// Example response (400)
{
  "error": "Invalid IP address format",
  "code": "invalid_ip",
  "details": {
    "provided": "not-an-ip",
    "expected": "Valid IPv4 or IPv6 address"
  }
}
```

### Error Creation Helper
```typescript
function createErrorResponse(
  error: string,
  code: string,
  status: number,
  details?: Record<string, unknown>
): NextResponse<APIError> {
  const errorBody: APIError = {
    error,
    code,
    ...(details && { details }),
  };

  // Validate error response with Zod
  const validated = apiErrorSchema.parse(errorBody);
  return NextResponse.json(validated, { status });
}
```

**Key Features**:
- Validates error response structure (Zod)
- Consistent response format
- Optional details field for debugging
- Type-safe error handling

## 3. SERVICE LAYER ERROR HANDLING (src/lib/services/geolocation.ts)

### Architecture
- **Type**: Shared async service function
- **External Dependency**: IPstack API (with graceful degradation)
- **Caching Layer**: Upstash Redis (optional, no hard dependency)

### Error Handling Strategies

#### 1. Missing API Key (Graceful Degradation)
```typescript
if (!apiKey || apiKey === 'your_api_key_here') {
  // No API key configured - return minimal result
  const version = detectIPVersion(ip) || 'IPv4';
  return {
    ip,
    version,
    cached: false,
    timestamp: new Date().toISOString(),
  };
}
```

**Pattern**:
- Doesn't throw on missing optional API key
- Returns partial data (just IP and version)
- Allows application to work without external API

#### 2. HTTP Response Errors (API Communication)
```typescript
if (!response.ok) {
  throw new Error(`IPstack API returned ${response.status}`);
}
```

**Pattern**:
- Checks response status
- Provides specific error info (HTTP status code)
- Lets catch block handle actual exception

#### 3. API Error Response (Structured Error)
```typescript
if (data.success === false && data.error) {
  console.error('[IPstack Error]', data.error);
  throw new Error(data.error.info || 'IPstack API error');
}
```

**Pattern**:
- Checks API-specific success flag
- Extracts error info from response body
- Logs detailed error for investigation
- Throws user-friendly error message

#### 4. API Fetch Error (Catch-all)
```typescript
catch (error) {
  console.error('[fetchFromIPstack] Error:', error);

  // Return minimal result on API failure
  const version = detectIPVersion(ip) || 'IPv4';
  return {
    ip,
    version,
    cached: false,
    timestamp: new Date().toISOString(),
  };
}
```

**Pattern**:
- Graceful degradation: returns partial data instead of throwing
- Logs full error for debugging
- Application continues with reduced functionality

#### 5. Redis Cache Errors (Optional Dependency)
```typescript
try {
  const cached = await redis.get<IPDetectionResult>(cacheKey);
  if (cached) {
    console.log(`[Cache HIT] ${ip}`);
    return { ...cached, cached: true };
  }
} catch (error) {
  console.error('[Redis Error]', error);
  // Continue without cache on Redis error
}
```

**Pattern**:
- Cache failures don't interrupt main flow
- Silently degraded (continues without cache)
- Logged for monitoring
- Application remains functional

### Service Architecture
```
getIPDetectionResult(ip)
├─ Try Redis cache first
│  └─ Gracefully degrade on cache error
├─ Fetch from IPstack API
│  ├─ Check API key existence
│  ├─ Validate HTTP response
│  ├─ Check API error response
│  └─ Gracefully degrade on any error
└─ Try to cache result in Redis
   └─ Gracefully degrade on cache error

Result: Always returns IPDetectionResult
        (full data if APIs work, partial if degraded)
```

## 4. CLIENT-SIDE HOOK ERROR HANDLING (src/hooks/use-ip-detection.ts)

### Architecture
- **Type**: Custom React Hook (Client Component)
- **State Management**: useState for multiple concerns
- **Network Retry Logic**: Exponential backoff (1s, 2s, 4s)
- **Request Timeout**: 5 seconds per fetch attempt

### State Definition
```typescript
export interface UseIPDetectionState {
  status: 'idle' | 'loading' | 'success' | 'error' | 'retrying';
  data: IPDetectionResult | null;
  error: string | null;
  retryCount: number;
  isTimedOut: boolean;
}
```

**Key Signals**:
- `status`: State machine for rendering (not just loading/success/error)
- `isTimedOut`: Distinguishes timeout errors from other failures
- `retryCount`: Tracks auto-retry attempts

### Error Detection & Classification

#### 1. Timeout Detection
```typescript
const response = await fetch('/api/detect-ip', {
  method: 'GET',
  signal: combinedSignal,
  headers: { 'Accept': 'application/json' },
});
```

**Pattern**:
- Uses AbortController with 5-second timeout
- Converts timeout to meaningful error message
- Sets `isTimedOut` flag for UI rendering

#### 2. HTTP Error Response Parsing
```typescript
if (!response.ok) {
  const error: APIError = await response.json();
  throw new Error(error.error || `HTTP ${response.status}`);
}
```

**Pattern**:
- Parses standardized API error response
- Falls back to status code if error message missing
- Throws formatted error for catch block

#### 3. Abort Error Handling
```typescript
catch (error) {
  if (error instanceof Error && error.name === 'AbortError') {
    throw new Error('Request timed out after 5 seconds');
  }
  throw error;
}
```

**Pattern**:
- Distinguishes AbortError from other errors
- Provides user-friendly timeout message
- Re-throws other errors for outer catch

#### 4. Retry Logic with Auto-retry
```typescript
const currentRetryCount = state.retryCount + 1;
const canAutoRetry = currentRetryCount < RETRY_CONFIG.MAX_RETRIES;

setState((prev) => ({
  ...prev,
  status: canAutoRetry ? 'retrying' : 'error',
  error: errorMessage,
  retryCount: currentRetryCount,
  isTimedOut: isTimeout,
}));

if (canAutoRetry) {
  console.log(
    `[IP Detection] Retry ${currentRetryCount}/${RETRY_CONFIG.MAX_RETRIES} after ${getRetryDelay(currentRetryCount - 1)}ms`
  );
  await performDetection(true);
}
```

**Pattern**:
- Auto-retries up to 3 times
- Transitions to 'retrying' state for visual feedback
- Logs retry attempts with timing
- Only shows error UI after max retries exceeded

#### 5. Cleanup on Unmount
```typescript
useEffect(() => {
  return () => {
    if (abortControllerRef.current) {
      abortControllerRef.current.abort();
    }
  };
}, []);
```

**Pattern**:
- Aborts pending requests on unmount
- Prevents memory leaks and state updates on unmounted components

### State Transitions
```
idle → loading → success
       ↓
       retrying → (success or error)
       ↓
       error (after max retries)
```

### Manual Retry Availability
```typescript
const canRetry = state.status === 'error' && state.retryCount >= RETRY_CONFIG.MAX_RETRIES;
```

**Pattern**:
- Manual retry button only appears after auto-retry exhausted
- User can attempt indefinite manual retries
- UI clearly indicates max attempts exceeded

## 8. VALIDATION WITH ZOD (src/lib/validations/ip-schema.ts)

### Validation Layers

#### Input Validation (Client → Server)
```typescript
export function validateIP(ip: string): boolean {
  return ipSchema.safeParse(ip).success;
}

export function validateIPv4(ip: string): boolean {
  return ipv4Schema.safeParse(ip).success;
}

export function validateIPv6(ip: string): boolean {
  return ipv6Schema.safeParse(ip).success;
}
```

**Pattern**:
- Safe validation (doesn't throw)
- Returns boolean for easy conditionals
- Supports both IPv4 and IPv6 validation

#### Output Validation (Server → Client)
```typescript
export const ipDetectionResultSchema = z.object({
  ip: ipSchema,
  version: ipVersionSchema,
  country_code: z.string().length(2).nullable().optional(),
  // ... more fields
  cached: z.boolean(),
  timestamp: z.string().datetime(),
});

// In API route:
const validated = ipDetectionResultSchema.parse(result);
return NextResponse.json(validated, { status: 200 });
```

**Pattern**:
- Validates API response before sending to client
- Ensures type safety across network boundary
- Catches data corruption or external API changes
- Throws if validation fails (caught by error handler)

## Summary of Error Handling Patterns

### Key Principles

1. **Graceful Degradation**
   - Missing optional APIs don't break the app
   - Partial data returned instead of hard errors
   - Application continues with reduced functionality

2. **User Experience**
   - Friendly, non-technical error messages
   - Clear indication of what failed
   - Retry options when applicable
   - Different styling for loading vs. retrying vs. error states

3. **Developer Experience**
   - Development-only detailed error info
   - Structured error responses with error codes
   - Contextual logging with module prefixes
   - Type-safe validation with Zod

4. **State Management**
   - Clear state machine (idle → loading → success/error/retrying)
   - Separate tracking for different concerns (isTimedOut, retryCount)
   - Auto-retry with exponential backoff
   - Manual retry after auto-retries exhausted

5. **Defensive Programming**
   - Input validation before processing
   - Output validation before returning
   - Type guards for error classification
   - Cleanup on unmount (AbortController)

6. **HTTP Status Codes**
   - 400: Client errors (invalid input, missing data)
   - 429: Rate limiting
   - 500: Server errors (API unavailable, validation failure)

7. **Error Response Format**
   ```typescript
   {
     error: string,                      // User message
     code: string,                       // Machine code
     details?: Record<string, unknown>   // Debug info
   }
   ```

### Error Handling Flow
```
User Action
  ↓
Client Hook (useIPDetection)
  ├─ Network Error/Timeout → Classify & Retry
  ├─ Parse API Error → Extract message & code
  └─ Update State (error, retryCount, isTimedOut)
       ↓
    Component Rendering
       ├─ Loading State → Skeleton UI
       ├─ Retrying State → Yellow warning UI
       ├─ Error State → Red error UI + Retry button
       └─ Success State → Display data
       
Server-side (API Route)
  ├─ Input Validation → 400 with details
  ├─ Process Request
  ├─ Output Validation → 500 if response invalid
  └─ Catch-all → 500 with generic message

Service Layer (Geolocation)
  ├─ Redis Cache → Graceful degradation
  ├─ External API → Graceful degradation
  └─ Always return data (partial if errors)

Error Boundary
  └─ Catch unhandled rendering errors → Show reset button
```
